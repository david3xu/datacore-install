# v0.1.82 — Your worker choices are kept in a file no install rewrites

**Type:** Distribution release on top of v0.1.80. **CLI helpers only.**

**The runtime bundle is unchanged and still reports `0.1.80`.** Nothing here rebuilds an image, so
the bundle archives attached to this release are byte-for-byte the ones v0.1.80 shipped. The tag
versions the installer and its CLI helpers, which `install.sh` fetches as separate assets.
`datacore doctor` and the install summary will say `0.1.80`, and that is correct.

## Fixed

- **An upgrade deleted the opt-in workers you had enabled — still, after v0.1.81 claimed otherwise.**
  v0.1.81 read the pre-upgrade choice from the registry mirror under `$DATACORE_HOME`. That file is
  outside the versioned bundle, but the bundle's own installer regenerates it *before* `install.sh`
  runs `datacore worker prune`, so during an install `prune` read a mirror that no longer recorded
  the choice. The v0.1.81 note was written from a `datacore worker prune` run by hand, which does
  recover, rather than from an upgrade, which does not. `RELEASES/v0.1.81.md` now carries a
  correction.

  Choices now live in `$DATACORE_HOME/worker-state.json`, a path no part of the bundle knows about,
  so no install rewrites it. It records two separate things: the families you enabled, and the
  provisioned worker identities with their tokens. Those are kept apart on purpose — a list of
  identities is not a list of choices, and treating it as one would enable every family whose CLI
  happens to be installed.

  Only `datacore worker add` and `datacore worker remove` change what you have chosen. `prune` never
  infers it from the registry it just wrote, because `prune` drops families whose CLI does not
  currently resolve: a single install with the binary off your `$PATH` would otherwise turn
  "enabled, not runnable right now" into "never asked for", permanently.

  Behaviour you should see: a worker you added survives an upgrade; a worker you removed stays
  removed; a worker whose CLI is temporarily missing is not dispatched to now but returns when the
  CLI does; a fresh install still enables only the lean default profile.

  Installs made by v0.1.79 or v0.1.80 have no choices file yet, so the first `prune` after upgrading
  migrates one: it reads what was enabled from the previous version's directory under
  `~/.datacore/versions`, writes the file, and from then on the file is the only source consulted.

- **The migration read the new bundle as if it were the old one.** `~/.datacore/versions` holds a
  `current` symlink beside the version directories, so the incoming bundle appeared twice under two
  names, and an unresolved path comparison let it through as "the most recent previous version".
  Paths are now resolved before comparison.

## Also

- `DATACORE_WORKER_DEBUG=1` makes `datacore worker prune` report the paths it resolved, the previous
  sources it found, the CLIs it detected and the choices it derived. Three diagnoses of the bug
  above were wrong because the install path was inferred from a local replay instead of measured.

- The CI job that tests upgrades asserted its result *after* a diagnostic step that restored the
  mirror and ran `prune` by hand, so it passed on a run where the upgrade itself had deleted the
  worker. It now asserts against the state the upgrade leaves, with nothing in between, and also
  checks the opposite error: that a worker you removed is not resurrected.

## Upgrading

```sh
curl -fsSL https://raw.githubusercontent.com/david3xu/datacore-install/main/install.sh | sh
```

Your data, your workers and your project map are kept.
