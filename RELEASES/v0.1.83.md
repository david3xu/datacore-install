# v0.1.83 — Any AI client can be a front door, with any model

**Type:** Distribution release on top of v0.1.80. **CLI helpers only.**

**The runtime bundle is unchanged and still reports `0.1.80`.** Nothing here rebuilds an image, so
the bundle archives are byte-for-byte the ones v0.1.80 shipped. `datacore doctor` and the install
summary will say `0.1.80`, and that is correct.

## New

- **`datacore connect` — make any AI client a front door.** A front door is the client you talk to:
  it reads the briefing, shapes tasks and wakes workers. Until now only Claude could be one. The
  bundle issues front-door credentials for Claude Code and Claude Desktop alone, and the only connect
  script it ships runs `claude mcp add`.

  Nothing in the Runtime required that. The Runtime picks a client's tool bundle by matching its
  agent id against role rules, and its own front-door credential holds exactly the same five scopes
  as every worker. What makes an identity a front door is its name. So:

  ```sh
  datacore connect muse --model muse-spark-1.3 --write
  ```

  creates `muse-front-door`, a separate identity so its actions are attributed to Muse and not to
  Claude. It writes one entry into Muse's settings, and the next Muse session has the front-door
  tools. Any client that runs MCP servers works the same way, using `--write=<path>` for its
  settings file, or no `--write` to have the entry printed instead.

  **Any model.** `--model` is a label shown by `datacore connect list`, nothing more. Datacore
  never launches a front door, so it has nothing to check a model against and accepts any. This is
  the opposite of a worker, which Datacore launches itself and therefore allowlists.

  **No secret in the client's settings.** The entry names a command, `datacore connect serve <name>`.
  The token lives in `$DATACORE_HOME/front-doors.json`, mode 600, written atomically, outside the
  versioned install so upgrades keep it. A corrupt file is reported and left alone rather than
  overwritten: the Runtime cannot hand a token back, only reissue it.

  **A front door directs workers; it does not configure them.** Of its 29 tools, the worker-related
  ones list workers and wake one for a task. Adding, removing or re-modelling a worker remains
  `datacore worker`, on the machine itself.

## Verified

Live, on a real install, not only in tests: Muse was connected this way, the Runtime served all 29
front-door tools to `muse-front-door`, and a new `muse exec` session on `muse-spark-1.3` called
`front_door_briefing` for a real project and answered from it — two model calls, none failed. That
is the first Meta model to answer through Datacore.

13 new regressions. Three were checked against deliberately broken versions of the code (a missing
tool-bundle header, no guard on names an earlier role rule would claim, a corrupt state file silently
replaced) and caught each one.

## Not verified in this release

- Front doors other than Muse were exercised only by the regression tests, not live. The entry is
  the standard `mcpServers` stdio shape, but each client's own loader is untested.
- **A Muse worker completing a dispatched task** — Datacore launching Muse to do work, rather than
  Muse calling Datacore — is still unproven. CI exercises that path with a stub launcher.
- Everything listed as not verified in v0.1.82 still applies.

## Upgrading

```sh
curl -fsSLO https://raw.githubusercontent.com/david3xu/datacore-install/v0.1.83/install.sh &&
sh install.sh
```

Your data, workers, project map and any connected front doors are kept. If you connected Muse with a
development checkout before this release, run `datacore connect muse --write` once after upgrading.
That repoints Muse's settings at the installed command, and it reuses the existing identity rather
than issuing a new one.
