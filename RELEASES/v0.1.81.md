# v0.1.81 — An upgrade stops deleting the workers you chose

**Type:** Distribution release on top of v0.1.80. **CLI helpers only.**

**The runtime bundle is unchanged and still reports `0.1.80`.** Nothing in this release rebuilds an
image, so the bundle archives attached here are byte-for-byte the ones v0.1.80 shipped. The release
tag versions the installer and its CLI helpers, which `install.sh` fetches as separate assets; it
has matched the bundle version until now only because every previous release changed both. A
rebuilt "0.1.81" bundle identical to 0.1.80 would be the misleading option, so the versions differ
here on purpose. `datacore doctor` and the install summary will say `0.1.80`, and that is correct.

## Fixed

- **An upgrade silently deleted every opt-in worker you had enabled.** `datacore worker prune` keeps
  one worker per family in the bundle's default profile and replaces the registry wholesale, and
  `install.sh` runs it on *every* install. An upgrade re-mints the registry with the full set, so by
  the time `prune` ran, the curated registry was already gone — and with it `agy`, `agy-review`,
  `muse-worker` and `muse-review`, whichever of them you had added. `datacore worker add muse`
  worked, dispatched, and was absent after the next install with nothing printed.

  The pre-upgrade registry cannot be recovered from the bundle, because `~/.datacore/current` is a
  symlink to a versioned directory and `generated/` belongs to the new version. Its mirror under
  `$DATACORE_HOME` is not versioned and `writeRegistry()` keeps it current, so it still holds the
  curated set at the moment `prune` runs. An explicit choice now outranks the default profile.

  A family whose CLI is no longer installed is still dropped — nothing could dispatch to it — and a
  fresh install, which has no mirror, behaves exactly as before.

- **`datacore worker prune` and `datacore worker add` disagreed about `muse`.** The selector resolved
  it while `installed_clis()` did not detect it, which is a second and independent way to lose a
  muse worker on reinstall. Both halves now agree, and CI asserts that every binary the selector
  resolves is one the detector looks for.

## Added

- `datacore report` is attached as an asset for the first time. It was named in `install.sh`'s
  `CLI_FILES` from v0.1.80 but not published, so `install.sh` correctly refused to put an unverified
  file on `PATH` and the verb did not exist on a real install.

- CI now runs the real `prune` code against the installed bundle's own catalogue across five cases:
  a chosen family survives an upgrade, an unchosen one is not resurrected, a fresh install is
  unchanged, an unreadable mirror falls back instead of aborting the install, and a choice whose CLI
  has gone is dropped. It covers whichever opt-in families a bundle declares rather than a list
  repeated in the test, and it carries a guard on itself: if the default-profile families were not
  kept, every case would read "dropped" and prove nothing.

## Upgrading

Install v0.1.81. If an earlier upgrade removed a worker you had enabled, re-add it once
(`datacore worker add muse`, `datacore worker add agy`) and it will survive from here on.
`datacore report` will tell you whether anything is still in the way of dispatch.
