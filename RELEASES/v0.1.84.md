# v0.1.84 — Connecting Muse as a front door no longer stops Muse workers

**Type:** Distribution release on top of v0.1.80. **CLI helpers only.** The bundle is unchanged and
still reports `0.1.80`.

## Fixed

- **`datacore connect muse --write` stopped every Muse worker from running.** v0.1.83 wrote a
  `datacore` server into Muse's global settings. The worker bridge injects its own `datacore`
  server into each Muse worker run, and Muse refuses an override that names a server its settings
  already define:

  ```
  muse: -c mcpServers.datacore: refusing run: the server name is reserved
  ```

  The task then sat leased until the Coordinator blocked it with `retry_budget_exhausted`. Nothing
  reached task state, and `datacore doctor` still read 22 ok, 0 fail. Muse found this itself, on its
  first dispatched task.

  Renaming the entry would not have been enough. A worker run loads every server in Muse's
  settings, so each autonomous worker would have inherited the front door's identity and tools.

  For a client Datacore also runs as a worker, `--write` now creates a launcher instead, and leaves
  that client's global settings alone:

  ```sh
  datacore connect muse --write
  muse-front-door
  ```

  `muse-front-door` starts Muse with the front door attached to that one session. Plain `muse`
  stays an ordinary session, and Muse workers get only their own server. Running the command again
  removes the settings entry v0.1.83 wrote, keeping a `.bak`. Only an entry that runs
  `datacore connect serve <name>` is removed, so a `datacore` server you configured yourself stays.
  Writing Muse's global settings by path is refused, and the refusal says why.

## Verified

Reproduced before the fix, using a model name that does not exist so that no call was billed. With
the entry present, Muse refused. Without it, the same injection passed. Under another name it also
passed, and that run showed every settings server being loaded into the run.

After the fix, live: through the launcher, the real `muse` started the real
`datacore connect serve muse` and reached the model call. 18 regressions, three of them confirmed
to catch deliberately broken versions (settings written anyway, a user's own entry removed, the
launcher's argument left unquoted).

## Not verified in this release

- **A Muse worker completing a dispatched task.** This release removes the thing that stopped it.
  The first real completion is the next measurement, not a claim of this release.
- Everything listed as not verified in v0.1.83 and v0.1.82 still applies.

## Upgrading

```sh
curl -fsSLO https://raw.githubusercontent.com/david3xu/datacore-install/v0.1.84/install.sh &&
sh install.sh
datacore connect muse --write
```

The last line matters if you ran `datacore connect muse --write` on v0.1.83. It takes the old entry
out of Muse's settings and writes the launcher.
